# 笔画·增强 (stroke_zh) 方案设计 v1.4

> 本文档记录方案的完整设计：目标、历史问题、调研结论（Google Gemini）、最终方案（含对调研建议的修改与理由）、验证结果。
> 最后更新：2026-08-17（v1.4.0 视觉块输入：词组改每字自然码连续串；词频换 jieba；简码扩 1~7 笔）

> **v1.3 → v1.4 升级须清空用户词典**：词组编码从「每字 4 笔」改成「每字自然码」，编码体系变了，旧用户词典按旧编码记录会出怪候选。

---

## 1. 设计目标与核心体验

- **输入方式**：五笔画（横竖撇捺折），键位 `h/s/p/n/z`，兼容 `d→n`、`t→h`、Mac 排位 `j/k/l/u/i`
- **核心 UX（用户实测定义）**：**每个字打 3 笔 → 常用字第一页上屏**
- 词组可打（每字前 4 笔连续打），但**绝不干扰单字输入**
- 纯离线，RIME 标准（元书输入法导入），iOS 字体全支持无乱码

## 2. v1.0 的问题（本版修订动机）

v1.0 = 单字 7953 + 雾凇词组 62 万（624,381 条词条 = 每词全码 + 4 笔简码各一条）。

实测问题（用户反馈 + 离线模拟证实）：

| 现象 | 数据 |
|---|---|
| 打 3 笔前缀时词组全参与竞争 | 每个 3 笔前缀命中 2,000~42,000 条词组 |
| 常用单字被挤出第一页 | 子 #35、天 #57、真 #179、太 #61（3 笔时） |
| 用户具体反馈 | 「我/这」打不出来 |
| 同词重复占位 | 全码 + 简码两条都命中前缀 → 同一词占 2 个候选位 |

**根因**：`enable_completion: true` 前缀联想下，3 笔输入会命中所有「编码以此 3 笔开头」的词组。词组量级过大时，单字（编码全码，最长 13 笔）在短前缀阶段毫无竞争力。

## 2.5 v1.2 的问题（v1.3 修订动机）

用户在真机实测（干净重装 + 空用户词典）：打 `szh` 三笔，「是」不在第一页。docs/REVIEW.md P0-1 已确认。

**根因**（librime `dict/dictionary.cc:73-84` 的候选排序）：同一次查询里先按 `remaining_code.length` **升序**排，再按权重降序。3 笔前缀下，「是」的全码 `szhhhshpn` 还剩 6 笔，而 8 笔词组码剩 5 笔 → 词组整段排在「是」前面。权重再高也翻不过来，因为剩余码长是主键。

`single_char_filter` 不能救：它遇到第一个 completion 类型候选就 `break`（`gear/single_char_filter.cc:41-45`），而 `table_translator` 给一切「剩余编码非 0」的候选都打 completion 标记（`gear/table_translator.cc:82-85`）→ 前缀联想段它一个字也管不到。

**唯一解**：把短前缀变成**精确匹配**，即给高频字建真简码条目（五笔/郑码/仓颉的通行做法）。见 4.1、4.6。

## 3. 调研：Google Gemini（2026-08-08）

调研问题：笔画输入法如何设计才高效（主流方案排序策略 / 简码体系 / 词组编码 / RIME 做法 / 权重策略）。

结论要点：

1. **单字与词组彻底分流**（iOS / 搜狗模式）：前 1~3 笔为「纯字禁飞区」，候选只展示单字；词组必须达到编码门槛（且精确匹配）才参选
2. **简码体系**：一/二/三级简码 = 取该字真实笔画前 1/2/3 笔 + 赋予高权重（5/25/125 槽位锁高频字）
3. **词组取码**：定长截取（二字词 = 首字前 2 笔 + 次字前 2 笔，总 4 笔；三字词 2+2+2；四字及以上前三末一）
4. **RIME 多 translator 分字典**：单字 translator `enable_completion: true` + 词组 translator `enable_completion: false`
5. **权重策略**：静态字频（国家语委频度表）+ 用户词典动态调频（`user_dict`）
6. Lua 过滤器兜底（输入 ≤3 笔时强制单字优先）

## 4. 最终方案 v1.3（采纳 + 修改）

### 4.1 与调研建议的差异（我们的修改与理由）

| 项 | Gemini 建议 | 我们的修改 | 理由 |
|---|---|---|---|
| 词组编码长度 | 每字前 2 笔（二字词 = 4 笔码） | **每字前 4 笔**（二字词 = 8 笔码） | 62 万词下 4 笔码仅 5⁴=625 个槽位 → 每码约 1,000 词灾难性撞码；8 笔码 5⁸≈39 万槽位 → 均码 <1 词，精确匹配可行 |
| 词组出现门槛 | ≥4 笔可参选 | **打满编码才出现**（二字词 = 8 笔） | 8 笔是词组最短码；配合 `enable_completion: false` 自然实现「禁飞区」 |
| 一/二/三级简码表 | 显式分配 5/25/125 槽位 | **采纳（v1.3 建表）**，名额按前缀发而非按字频前 N 名 | v1.2 的「不建表、靠前缀联想」是错的：前缀联想候选带剩余码长，`dictionary.cc:73-84` 按剩余码长升序排在权重之前 → 短码永远排在词组后。只有真简码条目才是精确匹配。见 2.5、4.6 |
| 词组全码 | 未提及 | **删除**（只留简码） | 全码太长无人打，且前缀阶段与简码重复占位 |
| Lua 过滤器 | 兜底保障 | **不用**；`single_char_filter` 也在 v1.3 移除 | 单字优先靠简码表实现，不靠 filter。`single_char_filter` 只重排开头连续的精确匹配段，遇第一个 completion 候选即 break → 前缀阶段零收益，留着只会掩盖真正手段。见 4.3 |
| 用户词典词组 | — | 学到的词组走主 translator，**仍可前缀联想** | 自动造词 encoder 公式与词组编码同规则（每字前 4 笔，逐字展开），见 4.4 |

### 4.2 数据层（构建产物）

| 文件 | 内容 | 权重 |
|---|---|---|
| `stroke_zh_base.dict.yaml` | **8,970** 条 = 单字全码 **7,953**（GB2312 6763 + 通用规范表 8105 基本区增量 1190，过滤 273 个扩展区字防乱码）+ 高频字简码 **1,017** | BLCU 25 亿字语料字频（`data/rime_ice_8105.dict.yaml` 权重列）；缺频次时退回 jieba；54 个高频无搭配字 ×100 |
| `stroke_zh_phrase.dict.yaml` | 词组 **309,416**（雾凇 54 万词，词频 ≥50 过滤，GB2312 字过滤，2~4 字，编码 ≥4 笔） | 雾凇词频 ×10 |
| `stroke_zh.dict.yaml` | 主表：**import base + phrase** + encoder 规则 | — |

词组条目 624,381（v1.0）→ 314,153（v1.2 去全码）→ 309,416（v1.3 砍 5/6 字词 `PHRASE_MAX_LEN=4`，砍 ≤3 笔码的伪词组 `PHRASE_MIN_CODE_LEN=4`）。

**base 表有 4 列**（`columns: text / code / weight / stem`）：`stem` 存该字的**全码**，简码行也写全码。原因见 4.4——自动造词的反查只取 `stem`，简码不会污染造出来的词的编码。

**单字权重换成字频表**（v1.3）：jieba 的单字项是分词词典副产物，量级 10³~10⁵，而词组权重是雾凇词频 ×10 = 10⁵~10⁸ → 打满 8 笔全码的单字（明/果/者/李/林）被同码词组压在第二页。BLCU 字频表量级 10⁵~10⁷，与词组同量级，单字才排得上去。

> **词组必须 import 进主表**：librime 部署时 `SchemaUpdate::Run` 只编译顶层 `translator/dictionary` 指向的词典。v1.1 曾把词组拆成独立 translator 的独立词典（stroke_zh_phrase），部署不编译它 → 运行时词组表不存在 → 词组完全打不出。v1.0 词组能打正因为词组在 `import_tables` 里（编译链完整）。

### 4.3 方案层（schema：单 translator + 简码表分流）

```yaml
engine:
  translators:
    - predict_translator
    - reverse_lookup_translator
    - punct_translator
    - table_translator   # 单字 + 简码 + 词组同一词典 (import_tables: base + phrase)
  filters:
    - uniquifier         # 去重 (同一词不会因简码/用户词典重复占位)
```

- **单 translator**：单字、词组同一词典（import 链完整 → librime 部署编译词组表，词组能打）
- **分流手段 = 简码表**（不是 filter）：1/2/3 笔是**精确匹配**的简码条目，排在所有前缀联想候选之前 → 打 1~3 笔第一页是高频单字；打满 8/12/16 笔（2/3/4 字词）词组精确出现
- **`single_char_filter` 已在 v1.3 移除**，理由（源码级）：
  - 它遇到第一个 completion 类型候选就 `break`（`gear/single_char_filter.cc:41-45`）
  - `table_translator` 给一切「剩余编码非 0」的候选都打 completion 标记（`gear/table_translator.cc:82-85`）
  - → 它只能重排开头的精确匹配段。而实测字频前 300 字打满全码时前面几乎没有词组（词组码是每字 4 笔，与单字全码几乎不撞），收益为 0
  - 留着它的真实代价：让人误以为「单字优先」已解决，掩盖真正手段（简码表），并掩盖 v1.2 的权重量级缺陷（见 4.2）
  - 这个性质现在由 `validate.py` 断言 4 直接测量，不靠 filter 保证

### 4.4 编码规则

| 对象 | 编码 |
|---|---|
| 单字 | 真实笔画全码（GB/T 25741 大陆笔顺，hspnz） |
| 高频字简码 | 全码的前 1/2/3 笔，作为**独立词条**入库（同字同码只发一条），见 4.6 |
| 词组 | 每字前 4 笔拼接（不足 4 笔打全部），如 我们 = `phshpsns`、中国 = `szhsszhh`；2~4 字词，编码 ≥4 笔 **（v1.4 起被自然码连续串取代，见 §8）** |
| 自动造词 | encoder 公式**逐字展开**：2 字词 `AaAbAcAdBaBbBcBd`、3 字词 12 位、4 字词 16 位（与词组规则一致）→ 学到的词进用户词典，可前缀联想 |
| 上屏预测 | predict.db（雾凇二元组），`max_candidates: 9` / `max_iterations: 3` |

> **encoder 公式必须逐字展开**：`algo/encoder.cc` 的 `Aa` 是「第 1 字第 1 码」，`U`~`Z` 是**倒数**索引（`Z` = 末字）。写 `AbBbCbZb` 之类的缩写公式，长词就会取错位；逐字展开的公式与词库编码逐位一致。
>
> **`stem` 列保护造词**：`UnityTableEncoder::TranslateWord` 先 `LookupStems` 再 `ReverseLookup`，反查表的取值来自 `set<string>`（字典序 → 简码排在全码之前），且 3/4 字词的 DFS 组合上限只有 32（`algo/encoder.cc:15`）。若不给 `stem`，反查会把简码当成该字的编码去拼 → 造出来的词编码错、或 DFS 被简码组合挤爆而漏掉正确编码。

### 4.5 权重策略

1. **静态字频**：单字 = BLCU《25 亿字语料汉字字频表》（雾凇 8105 表的权重列，量级 10⁵~10⁷）；词组 = 雾凇词频 ×10（量级 10⁵~10⁸）
2. **高频字加成**：54 个常用但少组词的字（的/有/个/是/在/了/我/你/他…）×100，打前几笔即靠前
3. **简码排序**：同一简码前缀内按字频降序发名额（见 4.6）
4. **动态调频**：translator 开 `enable_user_dict`——用户选过的字/词自动前置，越用越顺手

### 4.6 高频字简码表（v1.3 核心）

**名额按前缀发，不按字频前 N 名发**。每个前缀第一页只有 `PAGE_SIZE = 9` 个位置，发多了照样挤不进第一页。

单个前缀（如 `szh`）的 9 个位置这样分配：

1. **先扣占位**：该前缀上已有的精确匹配条目（全码正好等于这 3 笔的字、以及 ≥4 笔的词组不占位）
2. **再留位**：全码正好等于该前缀的字（十/口/工/士）无条件留一个位置——它们没有更长的码可退，简码挤掉它们就等于打不出
3. **余额按字频发**：剩下的位置给该前缀下字频最高的字

结果：`blocked + 留位 + 简码 ≤ 9`，该码上每个有字频的条目都在第一页。

**实测产物**：简码 **1,017** 条（1 笔 43、2 笔 204、3 笔 770）。字频 1-600 段的 3 笔第一页命中率 **19% → 71%**（见 5.1）。

## 5. 验证结果（离线模拟，2026-08-08）

> v1.3 起 `validate.py` 的校验项 5 是**冷启动排名回归**：按 `dict/dictionary.cc:73-84` 的规则（剩余码长升序 → 权重降序）重放全部 318,386 条词条，用户词典视为空，同权重取最坏名次。它不再只看少数代表字，而是逐段统计整张字频表。

### 5.1 单字 3 笔第一页命中率（按字频分段）

| 字频段 | 3 笔进第一页 | 命中率 | 断言下限 | 组合天花板 |
|---|---|---|---|---|
| 1-100 | 96/100 | **96%** | 93% | 98% |
| 1-300 | 263/300 | **87%** | 84% | 89% |
| 1-600 | 429/600 | **71%** | 68% | 73% |
| 1-1000 | 572/1000 | **57%** | 54% | 58% |
| 1001-2000 | 131/1000 | 13% | 11% | 13% |
| 2001-3500 | 80/1500 | 5% | 4% | 5% |

v1.2 同一口径的 1-600 段是 **19%**，v1.3 的简码表把它抬到 **71%**。

**天花板是组合上限，不是实现缺陷**：3 笔前缀共 5³ = 125 个，每个前缀第一页 9 位 → 全表只有约 1,100 个「3 笔第一页」席位。而字频前 600 的字只落在 104 个前缀上，且分布极不均（`szh` 一个前缀就压了 65 个高频字，`hsh` 38 个）。前 600 段的理论上限因此是 73%，实测 71%，差的 2 个点是 4.6 的「留位」规则——给十/口/工/士 这类无长码可退的字留席位，比多抬两个能退到 4 笔的字更重要。

**低频段（1001 名以后）本来就不该靠 3 笔**：简码名额已被高频字占满，这些字走 4 笔以上的前缀或全码。

**已知例外（4 个，`validate.py` 允许 4 个）**：`HIGH_FREQ_SINGLE_BONUS` 名单里的 最（前缀 `szh`）、都（`hsh`）、日（`szh`）、可（`hsz`）3 笔进不了第一页——它们撞在最拥挤的前缀上，且都有更短或更靠前的替代路径，属于组合无解。

**其他两条断言**：
- 字频前 30 字，3 笔全部 rank ≤ 9
- 字频前 300 字，**每个字都存在某个笔数能进第一页**（1/2/3 笔简码或全码，四者取其一）

### 5.3 预测（predict.db 纯后缀）

predict.db 由 `scripts/make_predict_data_ice.py`（雾凇词库）生成，value 为**纯后缀**（词「下一页」→ key=下 value=一页；key=下一 value=页）。librime-predict 候选为 0 宽度后缀，点击只上屏后缀 → 上屏「下」+ 点击「面」=「下面」，不重复。

> **v1.2 教训**：08-07 曾把 predict.db 的 value 改成「完整词」（下 → 下面/下载/下午），点击上屏整词 → 与已上屏字拼接 → 「下下面」。验证必须直接查 dist 里实际打包的 db（写 Darts + marisa 解析器），不能只看生成脚本。

## 8. v1.4 视觉块方案（词组编码修订）

### 8.1 动机（用户实测）

固定「每字 4 笔」不符合用户的**视觉块打字习惯**：按偏旁/字型自然停笔，笔数 3~5 笔不等。
实测（2026-08-17）：

| 字 | 用户自然打法 | 首部件 |
|---|---|---|
| 确 | 打"石"整块 5 笔 | 石（5 笔）|
| 当 | 打"⺌"整块 3 笔 | 小（3 笔）|
| 笔 | 打"竹"前缀 3~4 笔 | 竹（6 笔）|
| 认 | 打"讠人"整块 4 笔 | 讠（2 笔）+ 人 |
| 们 | 打"亻门"整块 5 笔 | 亻（2 笔）+ 门 |

固定 4 笔时：首部件 ≤4 笔的字打全即 4 笔（恰好）；首部件 =5 笔（石/禾/示/矢/可…）打全会**超过 4 笔** → v1.3 的词组码是 4 笔制，输入 5 笔+后续 = 超长 → 词条消失（prism 只按前缀匹配）。

### 8.2 自然码规则

每字一个自然码 = **整字全码的前 N 笔**：

| 首部件 | 自然码 = 全码前几笔 | 例 |
|---|---|---|
| 3~5 笔 | 打全部件（N = 部件笔画数）| 确=`hpszh`（石 5）、明=`szhh`（日 4）、当=`snp`（⺌ 3）、们=`psnsz`（亻门 5）|
| >5 笔或独体长字 | N = 4 | 我=`phsh`、国=`szhh`、笔=`phnp`（竹 6 笔打前缀）|
| ≤2 笔 | N = 4（凑整块）| 认=`nzpn`（讠人）、她=`zph`（女 3 笔 = 全码 3 笔直接打全）|

数据源：`data/chaizi-jt.txt`（kfcd/chaizi 拆字表，17951 字）+ `BUSHOU` 偏旁终止表（build.py 内置，~140 个常见偏旁，拆到偏旁即停）。递归拆解：字 → 首部件（chaizi 一层拆）→ 若部件可再拆且不在偏旁表则继续 → 停在偏旁表或不可拆处。

### 8.3 词组编码 = 自然码连续串（关键约束）

```
我们 = 我(phsh) + 们(psnsz) = phshpsnsz   （9 笔，连续无分隔）
确认 = 确(hpszh) + 认(nzpn) = hpszhnzpn   （9 笔）
```

**为什么必须连续串、不能空格分隔**：librime 编译词典时（`entry_collector.cc CreateEntry`），空格分隔 = 多音节 = 按空格 split 成多个音节**分别**进 prism 键集合；而 table_translator 只做**整键前缀匹配，不组合音节** → 空格编码的词组在 prism 里没有整键 → 用户实测"确认打不出、候选全是单字"。连续串 = 单个超长音节 = 整键进 prism = v1.3 的成熟机制，前缀匹配直接出词。

**不需要切分键**：连续串下用户连打自然码即出词（逐笔首现第 6~8 笔进第一页），皮肤恢复 v1.3 布局（无 delimiter 键）。

### 8.4 词组长度约束（librime 机制决定）

librime 候选排序主键是**剩余编码长度升序**（`dictionary.cc:73-84`），权重只是次级键：

| 码长 | 处理 | 原因 |
|---|---|---|
| <6 笔（4-5 笔）| **默认不收**；**A 方案例外**：jieba 词频 ≥ 10000 的超高频词放行（22 个：第一/一个/一些/一般/一定/一下/一次/一直/一起/一点…），且保留全权重（跳过 ×0.001）| 输入 N 笔时，码长=N 的词组精确匹配（remaining=0）永远排在更长编码的单字补全前 → 抢占单字 4-5 笔前缀（实测 4 笔命中率 98%→94%）。但「第一」这类必打词被误杀（用户实测打不出），放行后打满出词 rank≤3（第一=phnph rank 3）|
| 6-7 笔 | 权重 ×0.001 | 与单字 6-7 笔全码同码决胜，打折让单字第一、词组仍第一页 |
| 8+ 笔 | 正常（×717 提权后）| 与单字空间天然隔离 |

### 8.5 自动造词（stem = 全码）

- base 表 `stem` 列 = **全码**（不是自然码）：`UnityTableEncoder::TranslateWord` 查到 stem 后由公式取码，公式 `AaAb…` 固定取每字前 4 笔 → stem 必须 ≥4 笔，3 笔自然码的字（当/展/问）公式取第 4 笔会越界
- 自动造词走**公式 4 笔制**，与自然码词库并存：词库词打自然码，新学的词打 4 笔（词库 30 万已覆盖日常）

### 8.6 其他 v1.4 改动

- **词频（jieba）**：双库词（jieba 也有）用 jieba 词频（真实语料，常用词靠前）；雾凇独有词线性缩放到 jieba 量级（p50 对齐，不挤压）；词组整体 ×717 提权对齐单字字频表 p50（同码决胜不被字频表碾压）
- **简码 A′**：`SHORTCODE_LEVELS` (1,2,3) → (1..7)，单字任意笔数精确匹配；`BONUS_STRIP_MAX_LEN = 3` 解耦权重剥离（防 4-7 笔全码加成被剥）
- **打字效果回归**：`scripts/typing_test.py`（44 用例：词组连打 rank≤3 / 单字自然码 rank≤9 / 少打补全 / 4-5 笔排除特性断言），改编码后必跑，报告输出 `docs/typing_report.md`

### 8.7 实测效果（typing_test.py，2026-08-17）

44/44 通过：18 个日常词组连打 17 个 rank1、1 个 rank2；逐笔首现第 6~8 笔进第一页；少打 1 笔仍 rank1（我们/确认/社会/知道/他们）。单字自然码全部第一页（明 rank10 = szhh 拥挤前缀固有，允许例外）。
